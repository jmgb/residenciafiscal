# Lo que el repositorio declara que hay vivo en la base de datos.
#
# Es la respuesta a la sexta pregunta del subsistema: ¿la base de datos es la
# que el repositorio dice? Las demás ya tenían guardián —backup fresco, dump
# contra Supabase, checkout contra git—, y esta no. El 3 de agosto de 2026 se
# editaron en sitio dos migraciones ya aplicadas y producción se quedó ocho días
# con `private.purge_expired_deep_research_jobs` de un solo argumento mientras el
# repositorio la declaraba con tres; nada lo dijo hasta que un script del VPS la
# llamó y falló.
#
# Es una **allowlist**, no un diff del schema: aquí entra lo que sostiene un
# contrato o una garantía, no toda la base de datos. Tres tipos de línea:
#
#   firma       <schema.funcion>(<parámetros>)
#   restriccion <schema.tabla> <nombre> <definición>
#   columna     <schema.tabla> <nombre> <tipo>[ NOT NULL]
#
# Las firmas se escriben tal y como las imprime
# `pg_get_function_identity_arguments`, con los nombres de parámetro: un
# renombrado también rompe a quien llama por nombre. Las sobrecargas se declaran
# una a una y a propósito: sobra o falta cualquiera,
# `check-database-contract.sh` lo canta, y así se detecta también una firma
# antigua que sobrevivió a su sustituta.
#
# Al cambiar cualquiera de estas cosas en una migración hay que actualizar esta
# lista en el mismo cambio; `tests/test_database_contract.py` no deja que se
# olvide.

# Sin la cascada, un job creado a la vez que una supresión por derechos
# sobrevive a su conversación. La restricción no es una optimización: es la
# garantía.
restriccion private.deep_research_jobs deep_research_jobs_conversation_id_fkey FOREIGN KEY (conversation_id) REFERENCES private.chat_conversations(conversation_id) ON DELETE CASCADE
